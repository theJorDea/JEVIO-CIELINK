# Хранилище учебной CRM

`OperationStore` сохраняет **само действие**, а не попытку отправить его во внешнюю CRM. Сетевой вызов в боевую систему не выполняется. `crm_operations` — отдельная таблица симулятора. `session_id` передаётся вызывающим кодом и сохраняется без ссылки на локальную таблицу сессий; регистрировать сессию в CRM не нужно. Внешний ключ операции глобален: его использование в другой сессии считается конфликтом. Типы: `order` — заявка на подключение, `coverage_request` — только проверка покрытия, `handoff` — передача сотруднику. Согласие и актуальность условий до записи проверяет вызывающий код.

```python
from cielink.crm import OperationStore

store = OperationStore('sqlite:///crm.sqlite3')
request = dict(session_id='demo:call-17', operation_key='demo:call-17:confirmation-2', operation_type='coverage_request',
               confirmed_terms={'house_id': 'demo-42', 'revision': 2})
receipt = store.record_operation(**request)
assert store.lookup_operation(request['operation_key']) == receipt
assert store.lookup_reference(receipt.spoken_reference) == receipt  # поиск для оператора
```

Клиент слышит только `spoken_reference`: число от 1 до 99 999 999, уникальное среди всех сессий и типов операций одной CRM. Это не пароль. Номера могут иметь пропуски, не переиспользуются после удаления строки, при исчерпании запись завершится ошибкой. Оператор находит квитанцию через `lookup_reference` по уникальному индексу; `receipt_id` остаётся внутренним UUID. Простое «да» никогда не записывает действие. «Да, оформляйте» подтверждает только полностью доставленное актуальное предложение подключения.

Квитанция содержит `session_id` и `sequence_no`: номер действия внутри сессии, начиная с 1, в порядке записи, а не начала запроса. В PostgreSQL транзакция берёт advisory lock по хешу `session_id`; в SQLite блокировка писателя берётся до выбора следующего номера. Повтор и конфликт не расходуют номер.

Методы синхронные и не держат общего соединения. В асинхронном обработчике передавайте создание хранилища и каждый вызов в рабочий поток: `store = await asyncio.to_thread(OperationStore, url)`, `receipt = await asyncio.to_thread(store.record_operation, **request)`. Для поиска и восстановления используйте тот же подход. Отмена ожидания не прерывает работу потока: восстанавливайте результат по прежнему ключу.

Внешний ключ выбирают **до первой записи**: все попытки одного подтверждённого действия, в том числе из другого канала, используют тот же ключ. Новый ключ означает отдельное действие. Условия — снимок JSON-объекта со строковыми ключами, без NaN/Infinity; порядок полей не важен. После commit доступны `receipt_id`, `operation_key`, `operation_type`, `confirmed_terms`. Одновременные записи защищены уникальностью ключа в БД. Попытка поменять тип или снимок под тем же ключом вызывает `OperationConflictError`, исходная запись остаётся неизменной.

Если ответ потерялся или commit завершился тайм-аутом, не обещайте номер. Вызовите `store.recover_operation(**request)`: на новом соединении он сначала ищет квитанцию и сверяет тип и снимок. Только если ключ отсутствует, повторяет атомарную запись. Ошибка чтения не означает отсутствия ключа и передаётся вызывающему коду. Даже если первая транзакция завершится между чтением и повтором, второй записи не будет. Не переключайте БД при тайм-ауте: это другая область ключей.

## Запуск

- SQLite входит в Python. `sqlite:///crm.sqlite3` создаёт файл в текущем каталоге и применяет `002_operations.sql` и `sqlite/003_spoken_reference.sql` из `migrations` автоматически в транзакции, в том числе для существующих строк; родительский каталог должен существовать. Сохраняйте файл между запусками.
- Для PostgreSQL нужны psycopg 3 (`psycopg[binary]>=3,<4`), та же схема и обычный уровень изоляции `READ COMMITTED`. Примените `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/002_operations.sql -f migrations/003_spoken_reference.sql` к выбранной базе, затем передайте её `postgresql://...` в `OperationStore`. Пересоздавать том не нужно.
- `python -m pytest tests/test_crm.py` проверяет SQLite. Для тех же проверок PostgreSQL установите `CIELINK_TEST_POSTGRES_URL` на DSN **учебной тестовой базы**; тесты сами создают таблицу и используют уникальные ключи.
