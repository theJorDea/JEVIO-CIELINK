# Отраслевые аналоги: что проверить в телефонном подключении SkyNet

Вывод для кейса №2: голосовой подбор интернета уже существует. Отличие CIELINK стоит доказывать на поправке клиента: остались ли согласованы **сказанное агентом, карточка клиента и фактический результат в CRM**. Ниже — открытые описания, а не независимый аудит внедрений. Учебные контракты CIELINK не являются API SkyNet.

## Что проверить в прототипе

1. **Rules: ответ покрытия, с которым можно продолжить разговор.** На учебном адресе вернуть состояние `needs_clarification`, два идентификатора здания и различающий признак. Отдельные исходы: дом точно определён, но сведений нет; сеть точно отсутствует; технический сбой. Ни один из них не выбирает здание за клиента.
2. **Voice: не перебивать уточнением.** Проиграть одну запись «дом восемнадцать… корпус второй» и вторую с окончанием на слове «восемнадцать». В первом случае лишних вопросов ноль, во втором — только вопрос о корпусе. Проверки обеих гипотез допустимы только на чтение; устаревший результат отбрасывается.
3. **Клиентская карточка: защита от старой вкладки.** В согласии хранить идентификатор предложения и его ревизию. После смены дома сервер отклоняет старое подтверждение, даже если кнопка на телефоне всё ещё видна. Голосовое и экранное подтверждения одной версии не создают дубликат. Для демо хватит тестовой ссылки; SMS в пилоте — с разрешения, ограничением срока и без телефона или адреса в URL.
4. **Ops: сверка трёх независимых свидетельств.** Произнесённые условия проверять по аудио с таймкодом; показанную версию — по событию отображения на клиенте, не по отправке ссылки; выполненное действие — по квитанции CRM, не по намерению модели. Отображение не доказывает, что человек прочитал условия. Если нет дорожки или страница не была открыта, так и отметить.
5. **QA: намеренно сломать один шаг на стенде.** Клиент разрешил проверку адреса, агент это озвучил, а тестовая CRM вернула `installation_order`. Проверка должна отметить тип операции и таймкод согласия, а не выдать положительную оценку вежливому разговору. На новых версиях повторять без записи в боевую CRM.

| [Ростелеком: обслуживание действующего абонента](https://blog.rt.ru/b2c/kak-golosovoy-bot-rostelekoma-rabotaet-s-obrashcheniyami-abonentov.htm) | P2: повторный звонок по проверке дома. Не раскрывать историю только по определившемуся номеру; проверить общий семейный телефон и два обращения об отдельных квартирах. |
| [Dodo Engineering: эксперимент в Telegram](https://habr.com/ru/companies/dododev/articles/902856/) | P2: проверенную ошибку улицы переносить из разбора звонка в словарь и регрессионный тест. Добавлять отрицательный пример с созвучной улицей. Не переписывать исходный транскрипт. |
| [DoorDash / AWS: телефонная поддержка](https://aws.amazon.com/solutions/case-studies/doordash-bedrock-case-study/) и [Ask DoorDash: оценка агента](https://careersatdoordash.com/blog/building-ask-doordash-part-three-evaluation/) | P1: сверка обещаний с вызовами и квитанцией. Это разные продукты: практику проверки скрытых действий берём из второго, не приписываем её телефонному боту из первого. |
| [Xfinity: карточки тарифа](https://www.xfinity.com/support/articles/broadband-mobile-facts-labels) и [лист ожидания](https://www.xfinity.com/support/articles/appointment-waitlist/) | P2: различать «подтверждён вторник» и «хочу субботу». Никаких отмен текущего визита до согласия и подтверждения нового слота расписанием. |
| [Thiseas / Voice Logica](https://www.voicelogica.ai/en/case-studies/thiseas/) | P2: оценивать не число исходящих звонков подрядчика, а обратные звонки на состоявшийся монтаж и переносы. Без доступного расписания фиксировать пожелание, не бронировать выезд. |
| [Vodafone Visual Support](https://www.vodafone.com/news/newsroom/digital-society/vodafone-partner-techsee-is-helping-us-to-keep-customers-connected) | Вне MVP: специалист через камеру помогает определить оборудование. Для пилота сначала проверить, снимает ли это повторный выезд. Не просить снимать пароль или сохранять фото наклейки роутера. |
| [Hyperoptic: регистрация интереса](https://www.hyperoptic.com/support/new-customers/check-availability-and-register-interest) | P2: если отсутствие сети подтверждено, отдельно предложить уведомление о появлении покрытия. Не подписывать автоматически и не смешивать интерес, техническую проверку и заказ. |

**Демо:** один мобильный звонок, поправка корпуса, попытка подтвердить старую карточку, затем сверка в разборе. Если нет времени на экран, показать выдачу двух зданий и корректный итог в CRM: это уже проверяет пользу оркестратора. Остальные идеи не должны вытеснять основной результат кейса — номер подтверждённой заявки или подтверждение запроса на проверку.
