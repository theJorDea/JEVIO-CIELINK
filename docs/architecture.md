# Как устроен звонок и чему доверяет компания

Предлагаемая схема для хакатона. SIP и запись настоящие, а покрытие, заказы, монтаж и очередь сотрудников — учебные, пока SkyNet не согласует интеграции.

```text
мобильный → номер / АТС → SIP / LiveKit → потоковое распознавание
                                              ↓ partial / final
                                 состояние звонка + speculative orchestrator
                                      ↙                          ↘
                          адрес → покрытие → тарифы        ответ → потоковый синтез
                                      ↓                          ↓
                             подтверждение клиента         звук на телефоне
                                      ↓
                         заказ / проверка дома / очередь

дорожки + события + версия каталога + квитанция CRM
      → отдельная очередь → тяжёлая модель → эпизоды для проверки → тесты
```

## Состояние и границы решений

Модель извлекает намерение и пожелания, формулирует короткие реплики. Деньги, адрес, ID операции и допустимое действие приходят из проверяемых сервисов, а не из памяти LLM. Для старта: Python/asyncio, структурированные поля, SQLite или PostgreSQL; LiveKit SIP, **GigaAM-v4 RNN-T** для потокового ASR и потоковый TTS. GigaAM работает как локально развёртываемый адаптер, отдельный от оркестратора звонка. Поставщики заменяемы, выбор зависит от качества на телефонных записях, доступных ресурсов и требований к размещению. Не нужны векторная база для шести карточек и несколько агентов, спорящих о цене.

### Распознавание речи

Основная модель первой сборки — `v4_rnnt` из [GigaAM](https://github.com/salute-developers/GigaAM). Вызов создаёт поток на звонок с `streaming=True`; для начала использовать `future_context_ms=320`, затем проверить 160 и 640 мс на тех же записях. Partial — гипотеза для опережающего чтения, не подтверждённое поле и не основание для заказа. Перед использованием проверяются ревизии адреса и каталога; согласие на действие определяется отдельно.

SIP-аудио приводится к формату, который принимает модель, сохраняя непрерывность состояния потока. Телефонные кодеки, частоту дискретизации, преобразование аудио, задержку, точность корпуса и нагрузку проверяем на реальных контрольных звонках. Опубликованные метрики GigaAM не считаются результатом CIELINK. `GigaAM-Multilingual-v2 RNN-T` остаётся кандидатом для парного сравнения, если доступных ресурсов хватает.

Для локальной проверки ответов по умолчанию используется OmniVoice на CUDA, частота 24 kHz. При старте создаётся короткий эталонный фрагмент детерминированным seed с настройкой `male, middle-aged, moderate pitch`, затем его voice-clone prompt переиспользуется для всех ответов, чтобы тембр оставался постоянным между репликами и перезапусками. Это синтетический эталон, запись участника не нужна. Voice design для русского нестабилен. Kokoro-RU остаётся CPU-вариантом через `--tts-engine kokoro`, Silero TTS V5 — резервным вариантом через `--tts-engine silero`. В живом диалоге очередь аудио отменяется при перебивании, а уже сгенерированные, но не проигранные чанки не считаются услышанным ответом. Лицензия весов OmniVoice — CC-BY-NC, коммерческий телефонный запуск этой моделью не допускается без отдельного разрешения правообладателя.

LLM подключается через `ChatClient` с backend-ом `ollama` или `openai-compatible`. Адрес, модель и ключ берутся из переменных окружения. Для речевого теста LLM получает распознанный текст и формирует короткий ответ, который затем читает выбранный TTS-адаптер. Ключи не хранятся в Git. LLM не определяет покрытие, цены и допустимость оформления, не вызывает CRM и не заменяет явное согласие; эти решения принадлежат структурированному состоянию диалога и проверяемым адаптерам.

| Адаптер | Вход → результат | Ограничение |
|---|---|---|
| Адрес и покрытие | Исходная фраза → кандидаты с домом, дробью, корпусом, строением, литерой → статус по `house_id` | ГАР подтверждает адрес, не сеть. Различать `available`, `unavailable`, `unknown`, ошибку и неоднозначность. |
| Тип подключения | Явный выбор `apartment`, `private_house` или `business`, сохранённый в сессии | Не выводить тип из улицы или адреса. Условия бизнеса ведутся отдельной веткой. |
| Расчёт предложения | Дом, дата, сумма сегодня, месячный бюджет, потребности, версия каталога → 1–2 варианта или причина отсутствия | Для варианта: аванс на счёт, периоды и цены, обязательные доплаты, услуги, сроки и ограничения, URL и дата источника. Аванс не суммировать повторно как монтаж. |
| CRM / учебная очередь | Тип действия, `house_id`, подтверждённые условия, ключ операции → сохранённый ID и статус | Повтор того же действия возвращает тот же ID. После тайм-аута сначала запрос статуса; нельзя обещать номер до подтверждения. |
| Запись на монтаж (пилот) | Подтверждённая возможность + дата → свободные окна; выбранный слот + согласие → ID брони | Поиск можно начать заранее, удержание/бронь — не спекулятивны. Занятое окно не заменять молча. |

Кандидат в адрес нормализуется независимо от перечня подключённых домов. Если распознаны два корпуса, задаём один вопрос именно про корпус. Если человек находится за границей, спрашиваем, **где нужно подключение**. Подтверждённое отсутствие обслуживания — завершить подбор; неизвестное покрытие — предложить запрос на проверку. При сбое — пояснить, что проверить не удалось, предложить специалиста. При «подумаю» не создавать лид. Поломка у действующего абонента — не продажа: передавать контекст с согласия.

Публичная форма SkyNet загружает `https://skynet.ru/data/addresses.json`. `AddressCatalog` разбирает упакованные фиксированной длиной названия улиц и соответствующие им группы домов, затем кэширует исходный JSON в пользовательском cache на сутки. При сетевой ошибке использует последний корректный кэш. Значения статуса источника `0..3` сохраняются как `UNKNOWN`, `NEW`, `PLANNED`, `CONNECTED`; точное совпадение возвращает исходный `house_id`, отсутствие совпадения означает `unknown`. Каталог не является подтверждённым API заявки и не гарантирует фактическое подключение. `cielink-voice-server` ведёт отдельное состояние и ограниченную историю на каждую WebSocket-сессию; CLI standalone использует тот же каталог и консультационные правила. Тип подключения хранится отдельно от адреса.

Для учебной неоднозначности адаптер возвращает `needs_clarification`, список `building_candidates` и `clarify_field`. Например, если различается только корпус, продолжение реплики может разрешить выбор без вопроса. В необязательной клиентской карточке и голосе используем одну ревизию предложения. При записи сервер проверяет её актуальность независимо от канала подтверждения. [Протокол проверки на старой вкладке и расхождении с CRM](company-cases.md).

## Опережение без устаревшего обещания

1. Каждое изменение поля (`адрес`, `дата`, `бюджет`) получает ревизию. Отдельно различаем промежуточную гипотезу STT, финальный текст и осознанное согласие на действие. Устойчивость partial настраиваем на тестах, а не запускаем поиск по каждой букве.
2. Ключ чтения включает операцию и версии **её** входов. Покрытие зависит от дома, применимость предложения — от дома, даты и версии каталога, ранжирование — ещё и от бюджета. Ограничиваем число параллельных проверок; одинаковые объединяем.
3. При поправке отменяем зависимые задачи. Даже если отмена не дошла до сервиса, перед использованием результата сверяем ревизии. Негодный результат не попадает в текст, очередь TTS и карточку клиента. При перебивании сбрасываем очередь воспроизведения; начатая фраза не равно услышанные условия.
4. Перед оформлением пересчитываем применимость, коротко называем адрес и существенные условия. Изменились цена или дом — запрашиваем согласие снова. «Угу» на середине объяснения не создаёт заказ. Один ключ на одно подтверждённое действие.
5. Журнал событий: гипотеза → старт проверки → использована/отброшена и почему → реплика/перебивание → согласие → квитанция. На общей монотонной шкале звонка сохраняем ссылки на интервалы аудио. Отметка отправки аудио сервером не доказывает слышимость на телефоне.

## Что делать с двумя официальными ценами

Текст на веб-странице — вход для подготовки каталога, а не разрешение продавать по увиденной цене. Храним исторические снимки и приоритет утверждённых условий; при неразрешённом конфликте исключаем конкретное обещание и предлагаем уточнение. «От» — не персональная цена. Отдельно проверяем крайний день вступления в акцию и длительность скидки для абонента. В заявке фиксируем версию фактически предложенных условий; новая акция не меняет историю.

## Дашборд: два рабочих процесса вместо одного общего балла

**Разбор звонка.** Во время звонка видны текущий адрес, статус покрытия и ожидание согласия. После — список записей с исходом и причинами передачи. В карточке две дорожки, транскрипция по ролям, переход по таймкоду к обещанию, версия условий, отменённые проверки и фактическая запись CRM. Тяжёлая модель предлагает замечание с цитатой и интервалом. Сотрудник подтверждает или снимает его. При обрыве записи — «недостаточно данных». Ошибка постанализа не блокирует завершение звонка.

**Проверка обновления.** Из подтверждённого эпизода делаем обезличенный тест: входные факты, версия каталога, ожидаемый исход и запрещённое действие. Владелец тарифа запускает старую и черновую версии на одной выборке, видит «без изменений / другой вариант / требуется уточнение / нарушение». В строке — изменённое условие, старый и новый расчёт, ссылка на исторический фрагмент. Для проверки **новой произнесённой реплики** запускается отдельный диалог с симулятором: старое аудио не является доказательством нового поведения. До одобрения нет записи в рабочую CRM и публикации новых условий.

## Граница пилота

Достаточно одной ветки АТС. Быстрый откат — вернуть её на операторов. Контакт и запись доступны только тем, кому нужны; телеметрия использует случайный ID. Предупреждение о записи, место обработки, доступ к облачным моделям и сроки хранения согласуются до пилота. В Git — только учебные данные и добровольно подготовленные для публикации демонстрационные материалы. Детали испытаний — в [плане проверки](validation.md).
