# Как проверить адрес на слух, не подменив его ближайшим домом

**Решение для хакатона:** основной ASR оставить потоковым. Между промежуточным текстом и проверкой покрытия поставить небольшой адресный поиск. Поиск имеет право предложить несколько кандидатов **или ни одного**. Он не исправляет исходную запись разговора и не получает список домов с покрытием как единственно допустимый словарь.

## Десять работ: что полезно для SkyNet

Ниже — методы и границы переноса по доступным публикациям и аннотациям, не воспроизведение результатов. Число цитирований не служит критерием выбора.

| Первоисточник | Идея и решение для проекта |
|---|---|
| [Huang et al., Interspeech 2024](https://www.isca-archive.org/interspeech_2024/huang24f_interspeech.html) | Контекст подают в ранние слои энкодера, при обучении меняют написания. На LibriSpeech относительное снижение ошибки редких слов на 60% против отсутствия biasing и 25% против shallow fusion. Не результат для русских адресов и не настройка облачного API. |
| [Gong et al., BR-ASR, Interspeech 2025](https://www.isca-archive.org/interspeech_2025/gong25_interspeech.html) | Обучаемый поиск по аудио с похожими по звучанию отрицательными примерами сокращает большой список до кандидатов для ASR. Стоит перенять короткий список и трудные пары, не обещая воспроизвести модель простым поиском по тексту. Заявленные миллисекунды поиска — не задержка ответа в трубке. |
| [Sun et al., ICASSP 2024](https://arxiv.org/abs/2309.00723) | Языковая модель пересчитывает оценки готовых гипотез с контекстом имён. Уместно на втором проходе, **если** ASR отдаёт альтернативы; выбор из списка не восстановит вариант, которого там нет. |
| [He & Toda, PMF-CEC, TASLP 2025](https://arxiv.org/abs/2506.11064) | Фонемы, мультимодальные признаки и выборочная коррекция подозрительного фрагмента вместо переписывания всего текста. Полезен порог отказа от правки; факт изменения текста ещё не доказывает, какой корпус слышен в записи. |
| [Thorbecke et al., TSD 2025](https://arxiv.org/html/2409.13514v2) | Единое префиксное дерево для списка сущностей и контекста словных триграмм. Переносим идею роли соседних слов («на улице», «корпус»), но модификация beam search требует доступа к декодеру. В части экспериментов авторов список подготовлен с использованием эталона: для нашего теста так делать нельзя. |
| [Le et al., Interspeech 2021](https://www.isca-archive.org/interspeech_2021/le21_interspeech.html) | Потоковый ASR объединяет дерево префиксов, глубокий biasing и shallow fusion. Динамический словарь можно менять без переобучения готовой системы, но это не значит, что её архитектуру можно добавить поверх любого текстового API. |
| [Huber & Waibel, препринт 2026](https://arxiv.org/abs/2608.05759) | Сравнение Whisper с подсказками и трёх речевых LLM: на результат влияют посторонние слова в списке, их порядок и отличие спонтанной речи от чтения. Сообщаемые «до 88%» — относительное снижение ошибки на словах списка, не на всей речи. Проверить на звонке с самопоправкой, а не только зачитанных адресах. |
| [Yang et al., IEEE SLT 2024](https://arxiv.org/html/2411.06437v1) | По черновому CTC-тексту символьные биграммы и расстояние редактирования отбирают подсказки для LLM. Хороший образец дешёвого первого этапа. При увеличении списка со 100 до 2000 B-WER на LibriSpeech test-other выросла с 8,02 до 10,02%; нужные слова добавлялись из эталона. |
| [Taguchi et al., BaLEEN, препринт 2026](https://arxiv.org/html/2609.36913v1) | Сжатые представления ключевых слов можно подготовить заранее для замороженного речевого энкодера. Проверка на синтетической английской речи; тестовые подсказки содержали произнесённые ключевые слова без отвлекающих. Отложить внедрение, но обязательно проверить обратный случай: список есть, а клиент не назвал ни одного слова из него. |
| [Qiu et al., IEEE ASRU 2023](https://arxiv.org/html/2311.08966v1) | Потоковый transducer использует написание, фонемы и обучение на текстах с редкими словами. Отсюда идея сравнить фонетический поиск улиц с текстовым; это эксперимент с тем же принципом, а не воспроизведение обученной архитектуры. |

## Где можно выиграть

- **Только текст от облачного API:** нормализовать улицу и номер, различать дробь, корпус, строение, литеру; искать несколько вариантов в адресном справочнике с учётом уже названного города. Это поиск *после* ASR, а не улучшение акустической модели. Список кандидатов нужен для короткого вопроса, не для автоматической замены.
- **Доступны вероятности звуковой модели:** сравнить кандидатов по записи, а не только по написанию. [T-one](https://github.com/voicekit-team/T-one) выдаёт покадровые логарифмические вероятности букв русского алфавита, но штатный декодер работает по выделенным фразам. У [pyctcdecode](https://github.com/kensho-technologies/pyctcdecode) есть hotwords и настраиваемый вес. Предлагаемый тест: один раз получить вероятности по готовой фразе, декодировать с теми же параметрами без подсказки и с подсказкой. Проверить порядок меток, пробел, blank и соответствие словаря; совместимость не проверялась. Только после успеха сравнить работу на незавершённой реплике. Hotwords в [sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html) — другой путь, для transducer с modified beam search, не переключатель для CTC T-one.
- **Во время звонка:** на правдоподобной промежуточной версии разрешить фоновое чтение. При неоднозначности спросить: «Восемнадцать дробь два или восемнадцать, корпус два?» Не просить повторить всю улицу. На поправке устаревшие проверки отбрасываются. Степень совпадения со справочником сама по себе не является вероятностью правильного адреса.
- **После звонка:** сохранить разрешённый аудиофрагмент, исходную гипотезу и отдельно — интерпретацию дома с основаниями. Для спорных фрагментов сравнить дешёвый и более тяжёлый декодер. Расхождение попадает проверяющему, но не меняет запись CRM задним числом.

## Эксперимент, который можно показать жюри

Стартовая выборка: 12 пар коротких реплик × 2 говорящих = 48 записей добровольцев с учебными адресами. Включить редкие улицы, склонения, шум телефона, `18/2` против `18 к. 2`, исправление корпуса, верный дом без покрытия, улицу вне подсказок и реплики вообще без адреса. Несколько отложенных голосов и улиц для финальной проверки набрать отдельно; вес словаря и порог уточнения подбирать только на разработческой части. Не давать алгоритму район, если клиент его не назвал. Для контрольного примера поменять только покрытие дома при том же аудио: распознанный адрес **не должен измениться**.

1. Зафиксировать аудио, эталон полного адреса, допустимость уточнения и правильный бизнес-исход. Разметить отрезок адреса для измерения времени.
2. На одинаковой записи сравнить: обычное распознавание + точное сопоставление; тот же текст + поиск кандидатов; тот же поиск + выборочное уточнение. Отдельный эксперимент на одном локальном декодере — без hotwords / с hotwords. Не путать это сравнение с A/B/C оркестратора.
3. Считать по вариантам: найден ли правильный дом в первых трёх; правильно ли выбран полный дом без уточнения; сколько неверных адресов принято без вопроса; сколько верных пришлось переспросить; задержку до устойчивого правильного адреса и до первого содержательного ответа на телефоне. Отдельно показать случаи, где верного варианта нет в справочнике. Общий WER — вспомогательная метрика.
4. Выбирать режим по числу **правильных итогов** при сопоставимой доле уточнений. Если снизилась ошибка по словам, но появился неверный дом в заявке, режим не выпускать. Указать абсолютные числа, выборку и примеры ошибок; 48 записей — инженерная проверка, а не доказательство качества в пилоте.
